# Quality gates, тестирование и review

Дата: 2026-05-11  
Статус: draft for human review  
PRD: `PRD-Semeynyy-Byudzhet-iOS-2026-05-11.md`  
Архитектура: `docs/architecture/ARCHITECTURE-MVP.md`

## 1. Контекст

Проект разрабатывается в режиме AI-first with human-in-the-loop. Нужно зафиксировать, какие проверки обязательны до implementation и после implementation.

## 2. Цель

Определить единые quality gates для specs, tasks, реализации, тестов и review notes.

## 3. Scope

Входит:

- правила готовности spec;
- правила готовности task;
- definition of done;
- тестовая стратегия;
- review notes;
- human-in-the-loop checkpoints.

Не входит:

- конкретные feature tasks;
- CI/CD;
- App Store release process.

## 4. Spec readiness

Feature spec готов к task decomposition, если содержит:

- контекст и ссылку на PRD;
- цель изменения;
- пользовательские сценарии;
- функциональные требования;
- acceptance criteria;
- UI states, если есть UI;
- ошибки и edge cases;
- модель данных, если затронута;
- миграции, если нужны;
- стратегию тестирования;
- открытые вопросы.

Если открытый вопрос влияет на финансовые данные, приватность, миграции или scope MVP, он должен быть закрыт человеком до реализации.

## 5. Task readiness

Task готов к implementation, если содержит:

- ссылку на согласованный spec;
- конкретный результат;
- scope;
- out of scope;
- предполагаемые файлы или области кода;
- шаги реализации;
- тесты;
- definition of done.

## 6. Implementation gate

Код можно писать только если:

- есть PRD или product-описание;
- есть актуальный spec;
- есть task с ограниченным scope;
- нет критичных открытых вопросов;
- понятна стратегия тестирования;
- изменение не расширяет MVP без подтверждения.

## 7. Testing requirements

Приоритет:

1. Domain rules.
2. Use cases.
3. Mapping и persistence edge cases.
4. ViewModel states.
5. UI happy paths.

Финансовые расчеты должны иметь unit tests до того, как UI начнет на них опираться.

## 8. Review notes

Review note должен фиксировать:

- соответствие spec;
- найденные риски;
- тестовые пробелы;
- ручные проверки;
- что нужно перепроверить человеку.

## 9. Definition of done

Задача завершена только если:

- реализация соответствует spec;
- acceptance criteria выполнены;
- scope task не расширен;
- тесты добавлены или обновлены пропорционально риску;
- тесты запущены или причина пропуска указана;
- нет незакрытых критичных вопросов;
- изменения готовы к review человеком;
- финальный ответ содержит краткий итог, проверки и остаточные риски.

## 10. Human-in-the-loop checkpoints

Обязательное подтверждение человека нужно, когда:

- меняется product scope;
- появляется неоднозначное требование;
- решение влияет на архитектуру, данные, безопасность, зависимости или долгосрочную поддержку;
- изменение касается финансовых данных, Face ID, уведомлений или миграций;
- требуется новая внешняя зависимость;
- появляется предложение расширить MVP.

## 11. Acceptance criteria

- Любая будущая feature-разработка может ссылаться на этот spec как на quality gate.
- Reviews создаются в `docs/reviews/`.
- Tasks создаются в `docs/tasks/`.
- Decisions создаются в `docs/decisions/`, если решение долгосрочное.
- Отсутствие запущенных тестов всегда явно объясняется.

## 12. Принятые базовые допущения

- До появления Xcode-проекта и первых tests достаточно локальных запусков.
- После создания проекта нужно добавить минимальный build/test command в task definition и фиксировать результат в review notes.
