# AGENTS.md

Этот проект разрабатывается в режиме AI-first with human-in-the-loop. Все агенты должны работать по строгому Spec Driven Development: сначала согласованные спецификации и задачи, затем реализация, тесты и review.

Проект: iOS-приложение для учета семейных доходов и кредитной нагрузки.  
Основной продуктовый источник: `PRD-Semeynyy-Byudzhet-iOS-2026-05-11.md`.
Индекс документации: `docs/README.md`.

## 1. Язык и стиль работы

- С владельцем проекта общаться на русском языке.
- Product-документы, specs, tasks, decision logs и review notes вести на русском языке.
- Код, имена типов, функций, файлов, API и технические идентификаторы писать на английском.
- Финальные ответы должны кратко объяснять, что сделано, какие проверки выполнены и какие риски остались.
- Если требование неоднозначно, агент обязан остановиться и задать уточняющий вопрос или предложить 2-3 варианта с последствиями.

## 2. North Star продукта

Приложение должно заменить ручную таблицу Numbers/Excel для семейного планирования доходов и кредитной нагрузки.

MVP фокусируется на:

- участниках семьи;
- доходах: зарплата, премии, прочие доходы;
- кредитах и рассрочках с фиксированным графиком платежей;
- годовой таблице с переключением лет;
- деталях месяца;
- остатке "на жизнь";
- проценте кредитной нагрузки;
- локальном хранении;
- Face ID / Touch ID;
- простых локальных напоминаниях.

MVP не включает:

- банковские интеграции;
- импорт/экспорт;
- синхронизацию между устройствами;
- мультивалютность;
- учет всех ежедневных расходов;
- веб-версию или Android-версию.

Любое расширение MVP требует отдельного spec и подтверждения человеком.

## 3. Строгий Spec Driven Development

Feature-код запрещен без согласованного spec и task.

Канонический поток:

1. `PRD`
2. `Spec`
3. `Tasks`
4. `Implementation`
5. `Tests`
6. `Review`

Агент может писать код только если:

- понятна цель изменения;
- есть актуальный PRD или product-описание;
- есть spec с проверяемыми требованиями;
- есть task с ограниченным scope;
- известны затронутые модули или ожидаемая область поиска;
- понятна стратегия тестирования;
- открытые вопросы закрыты или явно приняты человеком как риск.

Если хотя бы один gate не пройден, агент не должен импровизировать. Нужно сначала создать или уточнить недостающий артефакт.

## 4. Обязательные артефакты

Перед работой с документацией агент должен открыть `docs/README.md` и использовать его как навигационный индекс по PRD, architecture, specs, tasks, decisions и reviews.

Рекомендуемая структура:

```text
docs/
  prd/
  specs/
    foundation/
    features/
  tasks/
    foundation/
    features/
  decisions/
  reviews/
```

### PRD

Фиксирует:

- цель продукта;
- пользователей;
- проблему;
- пользовательские сценарии;
- MVP scope;
- non-goals;
- ограничения;
- риски.

### Spec

Файл: `docs/specs/<category>/<human-readable-name>.md`

Примеры:

- `docs/specs/foundation/domain-core.md`
- `docs/specs/features/income-management.md`

Spec должен включать:

- контекст и ссылку на PRD;
- цель изменения;
- пользовательские сценарии;
- функциональные требования;
- acceptance criteria;
- состояния UI;
- ошибки и edge cases;
- модель данных, если затронута;
- миграции, если нужны;
- стратегию тестирования;
- открытые вопросы.

### Tasks

Файл: `docs/tasks/<category>/<human-readable-name>.md`

Task должен включать:

- ссылку на spec;
- конкретный результат;
- scope;
- out of scope;
- предполагаемые файлы или области кода;
- шаги реализации;
- тесты;
- definition of done.

### Decisions

Файл: `docs/decisions/<human-readable-name>.md`

Decision log нужен, когда решение влияет на архитектуру, данные, безопасность, зависимости или долгосрочную поддержку.

### Reviews

Файл: `docs/reviews/<human-readable-name>.md`

Review notes фиксируют:

- соответствие spec;
- найденные риски;
- тестовые пробелы;
- ручные проверки;
- что нужно перепроверить человеку.

## 5. Human-in-the-loop

Человека обязательно вовлекать, когда:

- меняется product scope;
- появляется неоднозначное требование;
- требуется архитектурное решение с долгосрочными последствиями;
- изменение касается финансовых данных, приватности, Face ID, уведомлений или миграций;
- агент хочет отступить от spec;
- тесты не могут подтвердить корректность;
- появляется новая внешняя зависимость;
- возникает соблазн расширить MVP.

Агент должен давать человеку короткие варианты выбора с последствиями, а не перекладывать на него весь анализ.

## 6. Использование сабагентов

Сабагенты используются для экономии контекста главного агента и параллельной работы.

Хорошие задачи для сабагентов:

- разведка по кодовой базе;
- анализ конкретного риска;
- подготовка черновика spec;
- декомпозиция spec на tasks;
- review конкретного slice;
- проверка соответствия реализации spec;
- поиск edge cases в расчетах.

Плохие задачи для сабагентов:

- "подумай обо всем";
- "сделай архитектуру проекта" без рамок;
- "реализуй фичу" без spec/task;
- задачи с пересекающимися файлами для нескольких worker-агентов.

Главный агент отвечает за стратегию, финальное решение, интеграцию результатов и общение с человеком.

## 7. Архитектура

Предпочтительная архитектура: layered monolith + vertical slices.

Проект остается единым iOS-приложением. Не дробить код на Swift Packages, модули или сложные границы без отдельного decision log.

Базовые слои:

- `Presentation`: SwiftUI views, view state, user interactions.
- `Application`: use cases и координация пользовательских сценариев.
- `Domain`: бизнес-сущности, value objects, правила расчетов.
- `Data`: SwiftData/Core Data models, repositories, mapping, persistence.

Vertical slice группирует код вокруг пользовательской функции, например:

- `FamilyMembers`
- `Income`
- `Credits`
- `YearlyOverview`
- `MonthDetails`
- `Settings`
- `Security`
- `Notifications`

Slice может содержать свои views, view models, use cases, domain helpers, repositories и mappers. Shared-код появляется только после 2-3 реальных повторов и понятной общей формы.

## 8. KISS

Выбирать самое простое решение, которое закрывает текущий spec.

Запрещено без явной причины:

- DI container;
- event bus;
- custom reactive layer;
- generic architecture framework;
- protocol/factory/service/manager на всякий случай;
- глобальный mock framework;
- преждевременное выделение `Core` или `Shared`;
- оптимизации производительности без измеренной проблемы.

Абстракция допустима, если она:

- уже уменьшает сложность;
- нужна для тестирования;
- скрывает нестабильную внешнюю зависимость;
- повторно используется в нескольких slice.

## 9. iOS, Swift и SwiftUI

Предпочтительный стек:

- Swift;
- SwiftUI;
- SwiftData или Core Data после отдельного решения;
- LocalAuthentication;
- UserNotifications.

Правила:

- SwiftUI views должны быть декларативными и небольшими.
- Бизнес-логика не должна жить в `body`.
- Расчеты денег, месяцев, графиков платежей и статусов должны жить в Domain/Application.
- Использовать системные API Apple, если они закрывают задачу.
- Не строить кастомную навигационную систему без spec и decision log.
- Preview добавлять для важных экранов и состояний, если это не требует тяжелой инфраструктуры.

## 10. Доменные правила

Критичные доменные области:

- `YearMonth`;
- расчет доходов;
- повторяющиеся доходы и override по месяцу;
- расчет графика кредитов;
- статус платежа;
- просрочка;
- остаток "на жизнь";
- процент кредитной нагрузки.

Эти области должны быть покрыты unit tests. Финансовые расчеты важнее визуальной полировки.

Для денежных значений использовать тип, безопасный для финансовых расчетов. Не использовать `Double` для доменной арифметики денег без отдельного решения.

## 11. Тестирование

Приоритет тестов:

1. Domain rules.
2. Use cases.
3. Mapping и persistence edge cases.
4. ViewModel states.
5. UI happy paths для критичных сценариев.

Обязательные проверки для финансовых расчетов:

- доход участника по месяцу;
- доход семьи по месяцу;
- кредитная нагрузка участника;
- кредитная нагрузка семьи;
- остаток участника;
- общий остаток семьи;
- процент нагрузки;
- генерация платежей по сроку кредита;
- просроченные и оплаченные платежи.

Если тесты не запускались, агент обязан явно сказать почему.

## 12. Definition of Done

Задача завершена только если:

- реализация соответствует spec;
- acceptance criteria выполнены;
- scope task не расширен;
- тесты добавлены или обновлены пропорционально риску;
- тесты запущены или причина пропуска указана;
- нет незакрытых критичных вопросов;
- изменения готовы к review человеком;
- финальный ответ содержит краткий итог, проверки и остаточные риски.

## 13. Запреты и guardrails

Агентам нельзя:

- писать feature-код без spec/task;
- расширять MVP без согласования;
- удалять или переписывать чужие изменения без явного разрешения;
- добавлять внешние зависимости без decision log;
- менять архитектурный стиль без согласования;
- смешивать UI-логику и persistence-детали;
- прятать сложность за расплывчатыми `Manager`, `Helper`, `Service`;
- считать будущие гипотезы текущими требованиями.

Если PRD, spec, task и код конфликтуют, источником истины считается последний согласованный артефакт. Агент должен остановиться и запросить подтверждение.
