# PRD: iOS-приложение для учета семейных доходов и кредитной нагрузки

Дата: 2026-05-11  
Платформа: iOS  
Рабочее название: Семейный бюджет

## 1. Обзор продукта и цели

Приложение помогает семье наглядно планировать доходы и кредитную нагрузку по месяцам. Основная идея вдохновлена текущей таблицей Numbers/Excel: пользователь видит месяцы, участников семьи, регулярные доходы, кредиты/рассрочки и итоговую финансовую нагрузку.

Главная цель MVP: заменить ручную таблицу удобным локальным iPhone-приложением, где можно:

- добавлять участников семьи;
- учитывать доходы по категориям;
- добавлять кредиты и рассрочки с графиком платежей;
- видеть общую семейную нагрузку по месяцам;
- видеть остаток "на жизнь" после кредитных платежей;
- отмечать платежи как оплаченные;
- получать простые напоминания о платежах.

Продукт не является полноценным трекером всех расходов в MVP. Фокус первой версии: доходы семьи и реальные кредиты/рассрочки с фиксированным графиком платежей.

## 2. Целевая аудитория

Основной пользователь:

- семья или пара, ведущая общий бюджет;
- пользователь, который сейчас ведет таблицу в Numbers/Excel;
- человек, которому важно видеть нагрузку не только сегодня, но и на несколько лет вперед.

Типичный пример:

- Алекс и Сара имеют отдельные доходы;
- у каждого могут быть свои кредиты/рассрочки;
- семья хочет видеть общий доход, общую нагрузку, остаток и понимать, какие месяцы будут тяжелыми.

## 3. Основные пользовательские сценарии

### Сценарий 1: Настройка семьи

1. Пользователь открывает приложение.
2. Добавляет участников семьи: например, Алекс и Сара.
3. Для каждого участника указывает доходы: зарплата, премии, прочие доходы.
4. Выбирает основную валюту в настройках.

Acceptance criteria:

- пользователь может создать минимум одного участника;
- участник имеет имя и список доходов;
- доходы группируются по категориям;
- общая сумма доходов семьи считается автоматически.

### Сценарий 2: Добавление дохода

1. Пользователь открывает форму дохода.
2. Выбирает участника семьи.
3. Выбирает категорию: зарплата, премии, прочие доходы.
4. Указывает сумму.
5. Выбирает повторяемость: регулярный доход или разовый доход по месяцу.
6. При необходимости изменяет сумму дохода в отдельном месяце.

Acceptance criteria:

- зарплата может повторяться каждый месяц;
- премии и прочие доходы могут быть разовыми или повторяющимися;
- пользователь может изменить сумму дохода только для одного месяца;
- изменения отражаются в итогах месяца и года.

### Сценарий 3: Добавление кредита или рассрочки

1. Пользователь открывает форму кредита.
2. Указывает название: например, "День рождения" или "iPhone 16 Pro Max".
3. Выбирает владельца кредита: конкретный участник семьи.
4. Указывает общую сумму кредита.
5. Указывает первый взнос, если он есть.
6. Указывает срок, месяц начала и месяц окончания.
7. Указывает ежемесячный платеж вручную или дает приложению рассчитать его.
8. Сохраняет кредит.

Acceptance criteria:

- кредит имеет название, владельца, сумму, срок и график платежей;
- платежи автоматически распределяются по месяцам;
- кредит отображается в общей семейной нагрузке;
- кредит отображается в индивидуальной нагрузке владельца;
- пользователь может редактировать кредит после создания.

### Сценарий 4: Просмотр главной таблицы

1. Пользователь открывает главный экран.
2. Видит таблицу/матрицу по выбранному году.
3. Для каждого месяца видит семейные итоги:
   - общий доход семьи;
   - общая сумма кредитных платежей;
   - остаток на жизнь;
   - процент кредитной нагрузки.
4. Переключает год, чтобы смотреть будущие периоды.
5. Нажимает на месяц для просмотра деталей.

Acceptance criteria:

- главный экран показывает данные по календарному году;
- пользователь может переключаться между годами;
- кредиты, выходящие за пределы текущего года, отображаются в будущих годах;
- остаток считается по формуле: общий доход семьи - кредитная нагрузка;
- процент нагрузки считается по формуле: кредитная нагрузка / общий доход семьи * 100%.

### Сценарий 5: Просмотр деталей месяца

1. Пользователь нажимает на месяц.
2. Видит детализацию по каждому участнику:
   - доходы;
   - кредитные платежи;
   - остаток на жизнь.
3. Видит список платежей месяца.
4. Может отметить платеж как оплаченный.

Acceptance criteria:

- детализация месяца показывает данные по участникам;
- для каждого участника считается остаток: доход участника - платежи участника;
- платеж можно отметить как оплаченный;
- просроченные неоплаченные платежи подсвечиваются.

### Сценарий 6: Напоминания о платежах

1. Пользователь указывает дату платежа по кредиту.
2. Приложение создает одно локальное уведомление перед датой платежа.
3. Пользователь получает напоминание.

Acceptance criteria:

- уведомления работают локально на устройстве;
- для каждого кредита можно включить/выключить напоминание;
- приложение запрашивает разрешение на уведомления;
- если разрешение не выдано, приложение продолжает работать без уведомлений.

## 4. Core features и функциональные требования

### 4.1 Участники семьи

Требования:

- создание, редактирование и удаление участника;
- имя участника обязательно;
- у участника могут быть доходы и кредиты;
- удаление участника должно предупреждать о связанных данных.

### 4.2 Доходы

Категории доходов MVP:

- зарплата;
- премии;
- прочие доходы.

Требования:

- доход принадлежит участнику;
- доход имеет категорию, сумму, период действия и повторяемость;
- повторяющийся доход может быть изменен в отдельном месяце;
- разовый доход применяется только к выбранному месяцу;
- доходы суммируются по участнику и по семье.

### 4.3 Кредиты и рассрочки

Требования:

- кредит принадлежит одному участнику;
- кредит имеет название, общую сумму, первый взнос, срок, дату начала, дату окончания, дату платежа, ежемесячный платеж;
- пользователь может ввести ежемесячный платеж вручную;
- приложение может рассчитать платеж по простой формуле: сумма после первого взноса / количество месяцев;
- платежи генерируются по месяцам автоматически;
- каждый платеж имеет статус.

Статусы платежа:

- запланирован;
- оплачен;
- просрочен.

### 4.4 Главная годовая таблица

Требования:

- гибридный интерфейс: таблица как основа, детали по нажатию;
- главный экран показывает семейные итоги, а не перегружает таблицу деталями по каждому человеку;
- пользователь может переключать годы;
- цветовая индикация нагрузки:
  - до 30%: зеленый;
  - 30-50%: желтый;
  - выше 50%: красный;
- статус платежей в ячейках отображается цветом.

### 4.5 Детали месяца

Требования:

- список участников;
- доходы по категориям;
- кредитные платежи участника;
- остаток по участнику;
- общий доход семьи;
- общая кредитная нагрузка;
- общий остаток;
- процент нагрузки.

### 4.6 Безопасность

Требования:

- Face ID / Touch ID при открытии приложения;
- fallback через системный код устройства;
- если биометрия недоступна, приложение должно объяснить это пользователю;
- финансовые данные хранятся локально на устройстве.

### 4.7 Настройки

Требования:

- выбор основной валюты;
- включение/выключение Face ID / Touch ID;
- включение/выключение уведомлений;
- просмотр информации о приложении.

## 5. Scope первой версии

Входит в MVP:

- iOS-приложение под iPhone;
- локальное хранение данных;
- участники семьи;
- доходы: зарплата, премии, прочие доходы;
- повторяющиеся доходы с ручной корректировкой по месяцам;
- кредиты/рассрочки с владельцем и графиком платежей;
- годовая таблица с переключением лет;
- детали месяца;
- отметка платежей как оплаченных;
- индикация просрочки;
- расчет остатка на жизнь;
- процент кредитной нагрузки;
- цветовая индикация нагрузки;
- Face ID / Touch ID;
- простые локальные напоминания о платежах;
- одна основная валюта.

Не входит в MVP:

- синхронизация между устройствами;
- семейная совместная работа через разные Apple ID;
- импорт из Excel/Numbers/CSV;
- экспорт в PDF/CSV/Excel;
- мультивалютность;
- автоматическая загрузка курсов валют;
- учет всех ежедневных расходов;
- подключение банковских счетов;
- сложная аналитика и прогнозирование;
- веб-версия или Android-версия.

## 6. Рекомендации по техническому стеку

Рекомендуемый стек для MVP:

- Swift;
- SwiftUI;
- SwiftData или Core Data для локального хранения;
- LocalAuthentication для Face ID / Touch ID;
- UserNotifications для локальных уведомлений;
- Charts framework опционально для будущей аналитики.

Рекомендация:

Для первой версии лучше использовать SwiftUI + SwiftData, если целевая версия iOS позволяет. Это ускорит разработку локального приложения с формами, списками, таблицами и связями между сущностями. Если нужна поддержка более старых версий iOS, стоит рассмотреть Core Data.

Целевая платформа:

- iPhone first;
- iPad можно оставить как future enhancement;
- минимальную версию iOS нужно определить отдельно перед разработкой.

## 7. Концептуальная модель данных

### FamilyMember

Поля:

- id: UUID;
- name: String;
- createdAt: Date;
- updatedAt: Date;

Связи:

- has many Income;
- has many Credit.

### Income

Поля:

- id: UUID;
- memberId: UUID;
- category: enum salary | bonus | other;
- title: String?;
- amount: Decimal;
- recurrence: enum monthly | oneTime;
- startMonth: YearMonth;
- endMonth: YearMonth?;
- createdAt: Date;
- updatedAt: Date;

Связи:

- belongs to FamilyMember;
- has many IncomeOverride.

### IncomeOverride

Используется для изменения повторяющегося дохода в конкретном месяце.

Поля:

- id: UUID;
- incomeId: UUID;
- month: YearMonth;
- amount: Decimal;
- note: String?;

### Credit

Поля:

- id: UUID;
- memberId: UUID;
- title: String;
- totalAmount: Decimal;
- downPayment: Decimal;
- monthlyPayment: Decimal;
- termMonths: Int;
- startMonth: YearMonth;
- endMonth: YearMonth;
- paymentDay: Int;
- reminderEnabled: Bool;
- createdAt: Date;
- updatedAt: Date;

Связи:

- belongs to FamilyMember;
- has many CreditPayment.

### CreditPayment

Поля:

- id: UUID;
- creditId: UUID;
- month: YearMonth;
- dueDate: Date;
- amount: Decimal;
- status: enum planned | paid | overdue;
- paidAt: Date?;

Связи:

- belongs to Credit.

### AppSettings

Поля:

- id: UUID;
- currencyCode: String;
- biometricLockEnabled: Bool;
- notificationsEnabled: Bool;

### YearMonth

Концептуальный тип:

- year: Int;
- month: Int.

Нужен для стабильных расчетов помесячной таблицы без привязки к конкретному дню.

## 8. Принципы UI и UX

Основной принцип: сохранить наглядность таблицы, но сделать ее удобной на iPhone.

Главный экран:

- годовая таблица или матрица;
- переключатель года;
- строки или секции по месяцам;
- семейные итоги по каждому месяцу;
- цветовая индикация нагрузки;
- быстрый переход в детали месяца.

Детали месяца:

- компактная сводка сверху;
- список участников;
- по каждому участнику: доходы, платежи, остаток;
- список платежей с возможностью отметить оплату.

Формы:

- отдельная форма добавления дохода;
- отдельная форма добавления кредита;
- поля должны быть короткими и понятными;
- суммы вводятся в выбранной валюте;
- даты выбираются через month/year picker там, где день не нужен.

Цвета:

- зеленый: нагрузка до 30% или оплачено;
- желтый: нагрузка 30-50% или платеж скоро;
- красный: нагрузка выше 50% или просрочено;
- нейтральный серый/синий: запланированные платежи.

## 9. Безопасность и доступ

Данные хранятся локально на устройстве. В MVP нет аккаунтов, серверов и синхронизации.

Требования:

- при запуске приложения включается проверка Face ID / Touch ID, если пользователь активировал защиту;
- при неуспешной биометрии используется системный fallback;
- данные не отправляются на внешний сервер;
- уведомления не должны раскрывать лишние детали, если это можно настроить.

Рекомендация для текста уведомления:

- нейтрально: "Напоминание о платеже";
- без суммы и названия кредита в push-тексте по умолчанию.

## 10. Интеграции с внешними системами

В MVP внешние интеграции отсутствуют.

Используются только системные iOS-возможности:

- LocalAuthentication;
- Local Notifications;
- локальное хранилище.

Не используются:

- банковские API;
- облачная база данных;
- iCloud sync;
- импорт/экспорт файлов.

## 12. Риски, ограничения и потенциальные сложности

### Риск 1: Таблица может быть неудобной на маленьком экране

Решение:

- использовать гибридный подход;
- на главном экране показывать только семейные итоги;
- детали участников раскрывать на отдельном экране месяца.

### Риск 2: Расчеты по месяцам могут стать источником ошибок

Решение:

- ввести отдельный тип YearMonth;
- покрыть тестами расчет доходов, платежей, остатков и процента нагрузки;
- избегать расчетов через произвольные строки дат.

### Риск 3: Пользователь может изменить кредит после создания

Решение:

- при редактировании кредита пересчитывать будущие платежи;
- оплаченные платежи не менять без предупреждения;
- явно показывать, какие месяцы будут затронуты.

### Риск 4: Уведомления зависят от разрешений iOS

Решение:

- приложение должно работать без уведомлений;
- показывать статус разрешения в настройках;
- давать понятный путь к настройкам iOS.

### Риск 5: Приватность финансовых данных

Решение:

- локальное хранение;
- Face ID / Touch ID;
- нейтральные тексты уведомлений.
